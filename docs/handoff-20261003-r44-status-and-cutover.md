### 1.2 看板：URL 带凭据 ⇒ 静默退化成离线 demo

无头浏览器实测发现的**新** bug（handoff 未记录）：

```
后端 /cpt/api/dashboard/snapshot  →  200 + 真实 BTCUSDT K 线
前端                                →  「暂无数据」+ 红色报错
```

报错原文：
```
Failed to execute 'fetch' on 'Window': Request cannot be constructed
from a URL that includes credentials: /cpt/api/dashboard/snapshot
```

`new URL(endpoint, window.location.href)` 会**继承** base URL 里的
`user:password@`，而 `fetch` 按规范拒绝带凭据的 URL。
看板挂在 nginx `auth_basic` 后面，用户用 `https://user:pwd@host/cpt/`
打开就会中招。

**危害等级比报错高**：它不是报错页，是**静默**降级 —— K 线空白、盘口全空、
结构详情全是 `—`，只有一条容易被忽略的红色横幅。

## 2. ⚠️ 顺带发现：cron 每天在「静默失败」

```
===== 2026-10-02T13:47:45Z 开始（源=eastmoney scope=placeholder）=====
===== 2026-10-02T13:50:15Z 结束 rc=0 =====
```

**2 分半钟，rc=0，看起来「成功」** —— 实际只算了 62 只就死了。

这比崩溃更危险：`rc=0` 让任何监控都看不出问题，而那 62 只其实**写进暂存表了**
（就是 §3 里那 97 只的一部分）。§4 的 bug 藏在「成功」的退出码里。

**建议**：`factor-recompute-daily.sh` 应当在日志里显式检查
`state.stopped` 字段并以非零码退出，否则「跑完了」和「跑死了」永远分不清。
（脚本本身逻辑没问题，坏的是**可观测性**。）

## 4. 切表方案

### 4.1 前提：必须「替换」而非「合并」

实测**孤儿日期 = 0**（暂存表每一行都能对上 `daily_bar`），
而生产因子表从 2023-06-15 起、`daily_bar` 从 2024-01-02 起。
合并式切换会把生产的过期孤儿行留下 —— 那正是 R36 之前
`daily_bar_raw.source` 那种脏数据形态。

### 4.2 我的建议：等补算跑完再切，一次切干净

**理由（比上一版更强）**：

1. 现在那 95.4% 是 **2169 只子集**的结论，而占位票一只都还没补算完。
2. 补算后重出报告，95.4% 才代表**全宇宙**。
3. 中途切表会让库里同时存在三种口径（已切 / 旧的 2125 只非单调 / 剩余占位 1.0），
   下游任何全表统计都会被拖偏。而「全表旧口径」至少自洽。

### 4.3 切表必须带的硬断言

```sql
-- 断言 1：暂存表覆盖度（应 ≈ 生产总票数）
SELECT count(DISTINCT code) FROM asel.ref_adjust_factor_v2;

-- 断言 2：无孤儿日期（已实测 = 0；切完必须仍是 0）
SELECT count(*) FROM asel.ref_adjust_factor_v2 v
WHERE NOT EXISTS (SELECT 1 FROM public.daily_bar b
                  WHERE b.code=v.code AND b.date=v.trade_date);

-- 断言 3：单调性（后复权因子必须单调不降）
--   现有的 2125 只 tx:fqkline 旧值栽在这里；切完这条必须大幅改善
SELECT code FROM (
  SELECT code, hfq_factor,
         lag(hfq_factor) OVER (PARTITION BY code ORDER BY trade_date) prev
  FROM asel.ref_adjust_factor) t
WHERE prev IS NOT NULL AND hfq_factor < prev * 0.999
GROUP BY code ORDER BY 2 DESC;
```
